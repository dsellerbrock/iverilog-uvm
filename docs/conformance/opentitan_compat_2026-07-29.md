# Running OpenTitan on this fork — first assessment (2026-07-29)

Question asked: can this simulator be used with OpenTitan?

Short answer: **yes for block-level RTL, and that is now demonstrated end to
end.** The unmodified OpenTitan UART IP — with the full TL-UL fabric,
command/data integrity (SECDED), the `prim` library, the alert/escalation
senders and riscv-dbg pulled in as dependencies — compiles and simulates
correctly under this fork after four compiler fixes landed alongside this
document. The UVM DV testbenches do **not** run yet; they are blocked
behind gaps listed below, not behind anything architectural.

Everything here was measured, not estimated. Commands are reproducible from
the "How to reproduce" section.

## What was tested against

- `dsellerbrock/opentitan` @ `ef575385` ("[manuf] Use the silicon_creator
  driver to compute hashes", 2025-11-11), branch `master`.
- The fork is a **clean upstream snapshot**: HEAD is an upstream commit by
  an upstream committer, on `master`, with no local modifications on top.
  Nothing about it is hacked or patched, and nothing in it needed changing
  for any result below. Every OpenTitan source file used here is
  byte-for-byte upstream.

## Toolchain plumbing: it already works

OpenTitan drives its hardware builds with FuseSoC, and **Edalize already
ships an `icarus` backend**, so no new flow had to be written:

```
fusesoc --cores-root=. run --target=default --tool=icarus --setup <core>
```

produces an `iverilog` command file (`.scr`) with the correct file order and
include paths, and a `Makefile` that calls `iverilog` and `vvp`. This works
for both RTL targets and the DV (`--target=sim`) targets, including running
OpenTitan's own generators (`regtool` for the register RTL, `ralgen` for the
UVM RAL model, `csr_assert_gen` for the CSR assertions).

Pin `fusesoc==2.4.5` (the version OpenTitan pins). 2.4.6 rejects OpenTitan's
`.core` files over an empty-fileset schema check. The generators also need
`hjson mako semantic_version mistletoe systemrdl-compiler peakrdl-systemrdl
pycryptodome`.

The only thing the Edalize backend does not do is pass `-g2012`, which is
mandatory for any SystemVerilog input. Pass it via `IVERILOG_OPTIONS`.

## Result: UART IP compiles and simulates

With assertions stubbed (`-DSYNTHESIS`, which OpenTitan's `prim_assert.sv`
already supports as a first-class mode) the UART core builds a **clean
1.1 MB `vvp` image with zero errors**.

A hand-written smoke testbench then drove the real DUT over TL-UL — with
integrity generated by OpenTitan's own `tlul_cmd_intg_gen` — and confirmed:

- a TL-UL `PutFullData` write to `CTRL` is accepted with no `d_error`,
- a `Get` read of `CTRL` returns exactly what was written (`0x08000001`),
- after pushing a byte to `WDATA`, `cio_tx_en_o` asserts and `cio_tx_o`
  actually serializes it out.

```
PASS: CTRL readback 0x08000001
PASS: cio_tx_o toggled (4 falling edges)
SMOKE TEST PASSED
```

That exercises the register file, the TL-UL adapter, the SECDED integrity
path, the FIFOs and the baud-rate generator — not a toy subset.

## The four fixes this required

All four are IEEE 1800-2017 conformance gaps, not OpenTitan-specific
accommodations. Each has a regression test in `ivtest/ivltests/`, and the
full gate (`ivtest` 3237 pass / 0 fail, VPI 94/94, negative 76/76) stays
clean.

### 1. `property_expr ::= ( property_expr )` (A.2.10)

A fully parenthesized property was a syntax error. This is the shape every
macro that wraps its argument emits — OpenTitan's `ASSERT` expands to
`assert property (@(posedge clk) disable iff (...) (__prop))` — so **every
OpenTitan assertion was unparseable**, and the parser lost module boundaries
afterwards, producing cascades of bogus "already declared" errors far from
the real cause.

Fix: add the production to `property_expr` (`parse.y`). Parens holding only
a sequence keep the existing sequence path via the shift/reduce resolution
on `)`. Test: `sv_assert_paren_property.v`.

### 2. A property may not start with `(` and continue as an expression

Deeper and **not OpenTitan-specific** — this breaks ordinary RTL:

```systemverilog
assert property (@(posedge clk) (x == 1) && (y == 2));   // was a syntax error
assert property (@(posedge clk) (a) ? b : c);            // was a syntax error
```

Root cause, from the bison state machine: in the state reached after `(` +
an expression (state 3106 of the generated parser) there is a
**reduce/reduce conflict on `)`** between

```
sva_seq_atom   : expression .     (parenthesized SUB-SEQUENCE)
expr_mintypmax : expression .     (parenthesized EXPRESSION)
```

Bison breaks reduce/reduce ties by declaration order, and `sva_seq_atom` was
declared first, so `(a)` always became a sub-sequence — after which no
expression operator could follow the `)`. (A comment in `parse.y` asserted
the opposite resolution; it was wrong.)

Fix: route the sequence's boolean leaf through a new `sva_bool_atom`
nonterminal declared *after* `expr_mintypmax`, handing the tie to the
expression reading. Grammar conflict counts are unchanged (497 s/r,
1162 r/r) — the resolution flipped, no new ambiguity was introduced.
Sequence parens (`(a ##1 b)`, `(a[*3])`) are untouched, because their
contents cannot reduce to an expression so no tie arises. Test:
`sv_assert_paren_boolean.v`.

### 3. Conditional operator loses the enum type (11.4.11)

`e = cond ? A : B` with both arms the same enum type was rejected with
"This assignment requires an explicit cast" whenever the condition was
4-state. Per 11.4.11 the result type is the common operand type; a 4-state
condition is a *value* concern (bitwise blending), not a type concern — and
refusing the type bought nothing, since the cast the user was forced to add
produces exactly the same bits.

This is the backbone of OpenTitan's security hardening
(`mubi4_bool_to_mubi`, `lc_tx_bool_to_lc_tx`, and the FSM state updates in
`prim_alert_sender` / `tlul_adapter_reg`). Fix: drop the 2-state guard in
`NetETernary::enumeration()` (`netlist.cc`). Genuine 6.19.3 violations
(literals, resolved array elements, resolved function returns) are still
rejected — `tests/negative/enum_implicit_cast.sv` still passes. Test:
`sv_enum_ternary_type.v`.

### 4. Size cast of a string literal (5.9)

`64'("GAL_XOR")` was rejected with "Cast base expression must be a vector
type". Per 5.9 a string literal is a packed byte array and behaves as an
unsigned integer constant in integral contexts. `prim_lfsr` selects its
polynomial this way, so this blocked AES and everything else instantiating
an LFSR.

Fix: exempt the literal (`PEString`) in `PECastSize::test_width`
(`elab_expr.cc`). A string-*typed* expression is still correctly rejected —
that is a dynamic type, not a vector. Test:
`sv_cast_size_string_literal.v`.

## Where it stands per IP (RTL only, `-DSYNTHESIS`)

| IP | Before | After | Remaining root causes |
|---|---|---|---|
| `uart` | 11 errors | **0 — builds and simulates** | — |
| `kmac` | 11 errors | 2 errors | variable index into packed multi-dim array |
| `spi_device` | 4 errors | 4 errors | parameter binding through package; packed assignment-pattern arity |
| `aes` | 2 errors (blocked early) | 7 errors (deeper) | variable index into packed multi-dim array |
| `hmac` | 9 errors | **compiler crash** | assertion failure in `elab_net.cc:695` |
| `otbn` | 60+ errors | 80 errors (deeper) | multiple-driver analysis; variable index; zero-width concat |

Lower error counts are not always the story — AES and OTBN went *up* because
the earlier errors stopped aborting the compile and revealed what was
behind them. That is progress, not regression.

## Remaining gaps, in rough priority order

1. **`elab_net.cc:695` assertion failure** (`hmac`). A compiler crash, not a
   diagnostic. `NetNet* PEIdent::elaborate_lnet_common_: Assertion
   'use_path.empty()' failed`. Crashes should be triaged ahead of missing
   features.
2. **Variable index into a packed multi-dimensional array** inside a
   function — `transpose[i][j] = in[j][i]` (`aes_pkg.sv:647`). Reported as
   "A reference to a net or variable (`i') is not allowed in a constant
   expression". Blocks `aes` and `kmac`; a common RTL idiom.
3. **`for` with multiple typed declarations** — `for (int i = 0,
   StateEnumT t = t.first(); ...)` (12.7.1). One declaration is supported,
   several are not. Blocks `prim_sparse_fsm_flop`, i.e. assertion-enabled
   builds of anything with a sparse FSM.
4. **Unbounded consecutive repetition `[*m:$]`** (16.9.2). The grammar has
   `[->m:$]` and `[=m:$]` but not `[*m:$]`, and the automaton's `rep_tail`
   has no unbounded encoding, so this is engine work rather than a grammar
   line. Blocks assertion-enabled `prim_alert_receiver`.
5. **Multiple-driver analysis** (`otbn`) — 38 "cannot have multiple
   drivers" plus 10 "also continuously assigned". Needs its own
   investigation; may be several distinct causes.

Items 3 and 4 only affect **assertion-enabled** builds. With `-DSYNTHESIS`
they are irrelevant, which is why UART builds clean today.

## UVM DV testbenches: not yet

`fusesoc --target=sim --tool=icarus` successfully generates the complete
`uart_sim` file list — 256 entries covering `dv_utils`, `csr_utils`,
`dv_lib`, `cip_lib`, the TL-UL/alert/push-pull/UART agents, the generated
RAL package and `tb.sv`. So the DV build is fully *plumbed*.

Compilation still stops in the RTL portion, which is compiled first, at gaps
3 and 4 above. **The DV/UVM code itself has not yet been reached by the
compiler**, so no claim can be made in either direction about how well the
UVM layer works — that measurement is gated on finishing the RTL gaps.
Closing items 3 and 4 is the next step to get a first real reading.

## How to reproduce

```bash
# tools
pip3 install 'fusesoc==2.4.5' 'edalize==0.6.3' \
    hjson mako semantic_version mistletoe systemrdl-compiler \
    peakrdl-systemrdl pycryptodome

# file list for an IP
cd <opentitan>
fusesoc --cores-root=. run --target=default --tool=icarus --setup \
        --build-root=/tmp/ot/uart lowrisc:ip:uart

# build + run
cd /tmp/ot/uart/lowrisc_ip_uart_0.1/default-icarus
iverilog -g2012 -DSYNTHESIS -suart -c lowrisc_ip_uart_0.1.scr -o uart.vvp

# UVM DV file list (needs the generators above)
fusesoc --cores-root=. run --target=sim --tool=icarus --setup \
        --build-root=/tmp/ot/uart_dv lowrisc:dv:uart_sim
```

The TL-UL smoke testbench used for the simulation result is
`docs/conformance/repros/ot_uart_smoke.sv`. Compile it alongside the UART
file list with `-sot_uart_smoke`.

## Honest caveats

- The simulation result is one IP block and one smoke test. It proves the
  path works; it does not certify UART behaviour against the spec.
- Assertions were stubbed for the passing build. OpenTitan's assertions are
  a real part of its verification value, and they are not running yet.
- 135 "constant selects in `always_*` processes are not fully supported"
  warnings are emitted during the UART build. They are warnings, not
  errors — the process falls back to being sensitive to the whole vector,
  which is conservative and correct for simulation, but it means the
  sensitivity lists are coarser than written.
- Per this fork's own standing warning: treat all of it as guilty until
  proven innocent, and verify independently before relying on it.
